# macOS Control Strip and live permission status

Version **0.5.0** adds an option for keeping Apple's compact Control Strip available alongside Touch Bar Studio, changes keyboard-control labels to use the permission status reported by the running app, and preserves open submenu state when the same active profile is selected. Frontend/native builds and focused state, policy, slider, and fixture checks passed. Physical system-control behavior and keyboard/media delivery under a current-build authorization remain unverified.

### Keep the macOS Control Strip

Under **Appearance**, enable **Keep macOS Control Strip**. It applies immediately and is saved with the workspace. The preference is intended to keep the native compact controls available while the custom Touch Bar is active. When a Studio volume or brightness slider expands, it temporarily uses the full bar; **Back** is intended to restore the previous presentation. macOS may show the Control Strip beside the expanded bar, depending on the Mac and system behavior.

The existing Dock behavior is retained. Native compilation and focused tests for the Control Strip presentation policy passed. In the app UI, enabling the option took effect immediately and survived quit/relaunch while the custom Touch Bar remained On and the saved Dock layout remained. Physical Control Strip expansion and system Touch Bar presentation have not been verified on hardware.

Selecting the same effective visible profile again skips a redundant Touch Bar rebuild, preserving an open submenu or expanded slider. Native checks cover nested app matching and blacklist transitions. A different effective profile still uses the existing Touch Bar transition. Visible focus flicker on the physical Touch Bar was not verified.

### Permission status

Keyboard-control labels now reflect the Accessibility trust check available to the running app when that status is known. Hardware support and Automation access remain separate requirements. The check is performed quietly; Touch Bar Studio does not request access at launch.

On the current test Mac, **Device Control and Data Access** is On for an earlier ad-hoc app build. A read-only TCC check confirmed its authorization is pinned to that build's code hash. The current app correctly reports Accessibility and event posting as unavailable, so its keyboard/media actions remain blocked until access is granted to the current build. After an ad-hoc rebuild, remove the old Touch Bar Studio entry, add the current app, grant access, and quit and reopen it. This prerelease does not claim that keyboard/media delivery works before that user action.

### Verification status

Passed: production frontend/native build, frontend state/catalog checks, native focus/nested/blacklist checks, three Control Strip policy cases, expanded-slider self-test, 41-entry fixture audit (36 runtime controls, five export-only controls), and app UI preference persistence across restart. Permission display checks showed Accessibility/event posting unavailable, Automation unknown, and Dock built in; the OS grant belongs to an earlier ad-hoc build. Pending: user reauthorization of the current build and keyboard/media action delivery after reauthorization. Physical Control Strip expansion and visible focus behavior remain unverified. Results are recorded in [the verification file](https://github.com/Caylum-Hudson/touch-bar-studio/blob/v0.5.0/VERIFICATION.md).

Source only; no installable binary is attached. Existing Dock behavior is retained.
